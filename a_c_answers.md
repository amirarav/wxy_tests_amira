## A1

Project codebase: https://github.com/ecanales23/11.C35-Final-Project-TOD

Live site: https://ecanales23.github.io/11.C35-Final-Project-TOD/

This was my team's final project for *Data Visualization and Society* (Spring 2026), done with the Metropolitan Area Planning Council. We looked at whether completed transit-oriented developments in Greater Boston provide affordable housing in proportion to the lower-income renters already living nearby. The site is built with Svelte and D3 and deployed to GitHub Pages.

A lot of my contribution was research and data preparation. For the website itself:

- I built the first version of our dashboard map, which included joining the project locations to the affordability data and setting up zoom and pan. I also added a color scale to show the affordability gap for each project, as well as tooltips and a legend. Later on, I added municipal and neighborhood boundaries to the maps.
- I worked on making the site easier to use and navigate, such as fixing a detail panel that was glitching and making it so users could click on part of an income chart to keep it selected. 
- I also worked on a lot of the layout and made the timeline and dashboard sections responsive so they’d work on different screen sizes.


## A2

Before actually building, I’d do more research on the neighborhood/community we’re planning for in order to tailor the site to them. For example, if many of the residents primarily speak another language, I would add a translated version of the site in that language. If it’s a low-income community, I would focus on making the site mobile-friendly (making buttons big enough to tap easily, keeping pages light so they load quickly on slower internet or limited data, etc.) since many people may use their phones to go online instead of a computer. I’d also add descriptions to the map and use proper semantic HTML, and any other steps needed to support screen readers and make it accessible. 

For the frontend, I would use JavaScript and Svelte. I have some experience with React, but more with Svelte. However, if the team at the NYC Department of City Planning works more with React (or another framework), I would use that instead so they can easily maintain the site in the future or replicate it. For the map, I’ve mostly used OpenStreetMap for basemaps, so I would keep that and use context layers from NYC Open Data and DCP, like MapPLUTO, zoning districts, community districts, subway and bus routes, parks, etc. For larger layers like MapPLUTO, which has thousands of parcels, I would convert it into vector tiles once I’ve clipped all the layers to the plan area. To build it, I would use MapLibre. I have more experience with Mapbox than MapLibre, such as in my [bikewatching](https://amirarav.github.io/bikewatching/) project, which maps bike-share traffic in Boston. I think MapLibre would be a better fit here since it’s open source and we’re working on a public city project. I’ve also used D3 with SVGs on my transit-oriented development project and Leaflet on other small projects. Our TOD project didn’t map many sites or census tracts, which is why we used D3, but it wouldn’t work as well here with thousands of parcels and a street basemap. I think Leaflet could also be used but MapLibre would be a better option since it’s natively built for vector tiles and Leaflet is better suited for raster tiles.

The backend would be FastAPI with PostgreSQL and PostGIS, which I’m familiar with through the “Who Owns Massachusetts” project at the MIT Spatial Analysis & Action Research Group, where I worked on the backend in summer 2025 and am working again this semester (the project also uses Mapbox to host its map layers). Like in that project, I would define the database table with SQLAlchemy and GeoAlchemy2. It would have a PostGIS point geometry column for saving the location of the comment, the comment text, the layer name and feature ID if the user selected a feature (the BBL for parcels in MapPLUTO), and name and email if they filled those out. When the user clicks on the map, I would use MapLibre’s click event to get the coordinates for the pin, and *queryRenderedFeatures* (which I haven’t used before but found while researching this) to check whether they tapped a parcel and get its BBL. A comment form would then open and they can write their comment and optionally add a name and email. When they submit, the site will send everything to one FastAPI endpoint, which validates the fields and checks in PostGIS that the point is inside the plan area before storing it. This endpoint would only receive comments and there’s no public endpoint for reading them, so the comments wouldn’t be visible on the site. To read and export the comments, I would add authentication and then DCP staff or whoever else needs access could connect a GIS software directly or export GeoJSON, shapefile, CSV, etc. The first thing that came to my mind for this whole aspect was actually connecting the comments to Google Forms or Airtable since they can be exported easily, but they don’t store geometries so they would have be converted before they could be spatially joined to parcels.

I also assume that if we’re soliciting community input, there will be community meetings as well. I think it’s important to incorporate notes and feedback from those meetings into the online comments for analysis, especially from groups like elderly residents who might be less likely to use an online tool. We could have paper comment cards at these meetings that the team then adds afterwards (either through the website or straight to the database).

As a side, while working on the TOD project, to be honest, my teammates and I didn’t make efficient use of GitHub. We would commit straight to the main branch, even if some of the features we were implementing still had bugs, and then go back and fix them later. I’ve since gotten a lot more experience creating issues and pull requests, and that’s something I would definitely incorporate while working on this.


## C. Use of LLMs

I’ve used LLMs like Claude for code development, including on our TOD project for building features like the navigation bar and adding styles I hadn’t used before. I find it really useful as a starting point, especially when I’m working with a library or tool I’m not familiar with. I use it a lot to ask questions when I don’t understand something, and also to help debug errors and optimize my code. I always make sure I understand what it gives me and test it myself, since it isn’t always right. There have been times, especially when debugging, when it’s hallucinated functions or settings that don’t actually exist in the library, so when something doesn’t work I check the documentation.
